# CMS 全功能只读审计报告（2026-08-20）

## 结论

本轮没有修改业务代码、Directus 数据、数据库结构、权限、服务器配置或部署。审计确认 CMS 并非“整体正常”，共发现 5 项实际故障和 1 项测试覆盖缺口：

1. 已保存的文章封面公开访问返回 HTTP 403，新闻列表和详情页会引用无法显示的图片。
2. `news.cover_image` 仍是 `varchar`，但 Directus 元数据把它显示为文件选择器，并且缺少 `directus_files` 关系，属于未完成迁移。
3. 一条已发布新闻的 slug 末尾带空格，正常无空格 URL 会被重定向到新闻列表，带编码空格的异常 URL 才能打开。
4. `/zhibo-cangpei` 页面公开显示未解析变量 `{{shippingSla}}`。
5. 验收 Release 缺少 `cms:verify` 和权限验证命令依赖的脚本，部署服务器无法运行项目声明的 CMS 自检。
6. 现有自动化测试全部通过，但没有覆盖真实 CMS 的增删改、封面选择保存后重开、公开文件读取、slug 规范和功能标题变量替换。

因此，本次结果不能继续归结为“只需部署侧处理”。第 1、2、3、5 项涉及验收 CMS 数据、权限或部署；第 4 项是明确的仓库代码缺陷；第 6 项需要补测试。第 1 项还需要代码与部署共同确定公开资源交付策略。

## 已确认问题

### P1：Directus 文件公开读取被拒绝

- 验收 CMS 中唯一被文章引用的封面文件，通过 Directus `/assets/{id}` 匿名读取返回 403。
- 使用当前 Web 内容令牌读取同一资源仍返回 403。
- 通过验收站公开反向代理 `/cms/assets/{id}` 读取也返回 403。
- 新闻列表和详情 HTML 已输出该公开资源 URL，因此“上传成功”不代表网站能够显示该封面。
- 当前其他文件字段尚未填值；如果以后给案例、期刊、服务页或关于页选择 Directus 文件，也会受到同一资源访问策略影响。

责任范围：Directus 文件访问策略/反向代理属于 CMS 与部署配置；仓库需要增加真实资源可达性验证，避免只验证 URL 拼接。

### P1：新闻封面字段处于半迁移状态

- PostgreSQL 物理字段：`news.cover_image` 为 `character varying`。
- Directus 字段元数据：`file-image`，`special=file`。
- Directus 关系：不存在 `news.cover_image -> directus_files`。
- 两条已发布新闻中，一条保存了 UUID 形式的字符串，另一条为空。

这能直接解释“文件能上传，但选择封面没有作用或不能稳定回显”：后台界面按文件字段操作，底层数据契约却仍是普通字符串。

责任范围：CMS Schema/数据库迁移，不是重新发布 Web 包即可解决。迁移前必须备份数据库和附件，并单独授权。

### P1：已发布新闻 slug 含末尾空格

- 异常记录的 slug 为 `chehsi `，末尾包含一个 ASCII 空格。
- `/news/chehsi` 返回 302 并回到 `/news`。
- `/news/chehsi%20` 返回 200，但 canonical URL 也继承了异常空格。
- 正常记录 `/news/cheshi` 返回 200。

这就是“有时候 new/news 页面打不开文章”的一个已复现原因。当前契约只检查缺失或重复，没有检查首尾空白及规范化后的重复。

责任范围：现有 CMS 数据需要清理；仓库需要增加 slug 规范化校验和详情不存在时的测试。

### P1：直播仓配页泄漏未解析变量

- 验收站 `/zhibo-cangpei` 页面出现两处 `{{shippingSla}}`。
- 数据查询对功能项 `desc` 执行了变量替换，但 `title` 原样返回。
- 对应代码位于 `src/lib/directus-content-queries.ts` 的服务页 `features.map` 映射。

责任范围：明确的仓库代码问题，需要后续修改并增加回归测试；本轮按要求没有修改。

### P2：部署包无法执行声明的 CMS 自检

- `package.json` 声明了 `cms:verify` 和 `cms:verify-runtime-permissions`。
- 当前验收 Release 中缺少 `scripts/verify-production-cms.mjs` 和 `scripts/verify-runtime-permissions.mjs`。
- 服务器运行 `npm run cms:verify` 会报 `MODULE_NOT_FOUND`。

责任范围：部署制品清单/运维工具交付。需要决定将只读验证脚本随 Release 发布，或提供独立且版本锁定的运维审计包。

### P2：自动化测试会产生“全部通过但关键功能未测”的假安全感

本轮运行 6 个相关 Vitest 文件，共 61 项全部通过。测试仍未发现上述 5 项故障，原因包括：

- `getDirectusAssetUrl` 仅验证字符串拼接，没有请求真实资源。
- CMS Setup 测试允许旧字符串字段继续存在，并验证跳过文件关系的兼容行为。
- E2E 中“supports CMS publishing”只检查新闻页面和分类文案，不执行真实发布流程。
- 没有 slug 首尾空白或规范化冲突测试。
- 没有覆盖服务页 `features.title` 的公开变量替换。
- 没有从部署 Release 内实际执行 CMS 自检命令。

## 已通过的只读检查

- 19 个预期集合全部存在；活跃内容集合数量与状态分布正常。
- 100 条 FAQ 均为 `published`，17 个页面键的关系、计数和归属一致，验收站 FAQ 查询正常。
- 使用真实运行时内容令牌执行 49 组查询，13 个活跃集合、17 个 FAQ 关系过滤、案例和服务详情均成功。
- 现有运行时权限验证通过：内容令牌与联系表单令牌分离，联系表单令牌为 create-only。
- 27 条 CMS 驱动公开路由使用 CMS 原始 slug 请求时均返回 200；sitemap 共 29 条 URL，均返回 200。异常新闻 URL 因 sitemap 也沿用了带空格 slug，不能视为 slug 正常。
- 63 个内容中引用的静态资源均可访问；Directus 文件资源不在此列，且已单独确认返回 403。
- 单例集合数量正确，必填内容未发现空值，状态值、新闻分类、发布日期、期刊 `is_latest`、嵌套 stats/features 结构均通过检查。
- 富文本未发现 `<script>`、事件处理器或 `javascript:` URL。
- 联系接口空请求返回 400 和预期校验错误，没有创建真实线索。

## 本轮没有覆盖的写入型功能

受 `AGENTS.md` 约束，真实 CMS 写入、权限修改和迁移必须单独明确授权。本轮没有执行：

- 新建、编辑、发布、取消发布和删除文章；
- 上传临时文件、选择封面、保存后重开和清理测试文件；
- 联系表单成功提交并核对后台记录；
- Directus 角色、版本、修订记录和回滚操作。

Chrome 自动化在本轮无法稳定接管已登录的 Directus 标签页，因此也没有把后台 SPA 能加载等同于完整 CMS 功能已通过。后续若获授权，应使用带统一测试前缀的草稿记录和一次性图片，完成创建、保存、重开、发布、前台读取、取消发布、删除及附件清理的闭环。

## 责任归类和建议顺序

1. CMS/部署先处理公开文件 403，明确匿名资源读取策略或受控资源代理，并验证新闻封面真实 URL 返回 200。
2. 备份后迁移 `news.cover_image` 为 UUID 文件关系，确认后台选择、保存和重开均一致。
3. 清理带尾随空格的新闻 slug；迁移前检查 trim 后重复，避免唯一键冲突。
4. 仓库修复服务页功能标题变量替换，并补充测试。
5. 仓库补充 slug、真实资源可达性、后台发布闭环和部署制品自检测试。
6. 部署侧恢复可执行的 CMS 审计工具后，再分别对验收站与主站运行同一套检查。

以上动作均未在本轮执行。
