## 实施设计

- 使用单进程封装包根公开的 experimental `dev()` API，集中兼容检查；不使用 Astro 私有后台标记、内部模块或锁文件字段，不引入进程监督与自动重启框架。
- 增加明确的 `dev:local` 命令及必要资源准备钩子，固定脚本所属项目 root、development 和 loopback。只允许选择本机端口，不允许注入远程依赖或任意监听地址。
- 当前 Astro 配置在模块顶层自行按 `process.argv` 读取 mode，单独给 `dev()` 传入 mode 不能覆盖这一步。包命令固定 `--mode development`；启动器拒绝其他值及重复冲突参数，直接 Node 调用时也先规范化 `--mode=development` 到 argv，再动态加载 Astro 并传入同值。用隔离的 development/production sentinel 夹具验证，不读取真实环境文件内容，也不改公开 origin 安全配置来适配启动器。
- 占用端口的归属由 Linux `/proc` 的 socket、PID、cwd、命令以及本地页面和已有 logo hash 一起核对；PID 不硬编码。权限不足、归属不明或页面错误时明确失败，不终止对方。
- 启动器自己的 Ready 仅在身份 HTTP 检查通过后输出；通过公开 `logLevel: error` 选项（保留编译/HMR 错误）避免上游在 HTTP 核验前打印的启动完成消息被误认成最终就绪。使用公开 strictPort 配置（如适用）并检查实际地址，不能在端口冲突时偷偷换号。
- 新实例持有 `DevServer` 后才允许调用其 `stop()`；就绪须有真实中英页面响应。启动中尚未返回 API 句柄的超时/信号由专用进程退出回收资源，并通过实际生命周期测试确认没有遗留。
- 阶段 2、3 会改变源快照。最终速度对照应在同一个阶段 1–3 完成后的副本中仅切换启动入口，重新取成对基线；早期 10.8/8.6 秒仅作诊断参考，不能直接用于声明最终提速。最终超时与性能预算在该阶段开工采样后冻结。

## 开工前只读预检补充

- 当前 Astro 7.2.8 的 `dev()` 会单独检查更新，telemetry 禁用不等于更新检查禁用。旧初步基线日志实际出现新版本提示，因此不能声称该早期采样无任何外连。最终新旧采样都在动态 import 前设置 `ASTRO_TELEMETRY_DISABLED=1`、`ASTRO_DISABLE_UPDATE_CHECK=true`；该更新检查开关集中于启动器，不使用私有后台绕过标记。
- 严格端口准确入口为公开 inline Vite 配置 `vite.server.strictPort=true`，Astro 顶层 server 无该字段；handle 返回仍须核对 loopback 与请求端口，覆盖 `/proc` 检查与 bind 间的竞争。
- 信号处理在动态 import 前安装。未取得 handle 的 timeout/signal/rejection 不能只设置 exitCode 或留下未完成的 Promise，须明确退出专用进程；取得 handle 后一次性 stop，第二次信号/停止超时可强制退出本进程。独立测试须观察端口与自有进程均消失。
- 复用的进程类型限 Astro dev 或本项目 local-dev，不能将 `server.mjs` 的构建服务当成有 HMR 的开发服务；核对公开 dev/HMR 入口。可信复用输出 PID/地址后立即 0 退出，不等待或接管既有服务生命周期。未知占用失败且保持对方不变。
- 成对速度仍用原前台 CLI 与新入口，同一白名单环境；另用公开 `--background` 覆盖旧 Agent 后台路径，单独报告，不混进六次前台基线。不得将不同启动模式的耗时直接计算为优化比例。
