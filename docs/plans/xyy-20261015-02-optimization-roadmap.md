## 第一阶段 发布稳定性

### 当前问题与处理方案

1. **健康与版本探针、formal 测试需要适配 HTTPS 契约。** 当前 canonical middleware 在 `/healthz`、`/version` 前执行；正式 HTTPS origin 下，本机 HTTP 请求也会收到重定向。覆盖范围应包括 `scripts/deploy.sh` 的健康检查和版本检查，以及 formal 的启动就绪检查、页面请求和 APIRequestContext。
   推荐利用已有可信代理契约建立专用本地测试启动器：子进程只监听 loopback，显式配置精确的 loopback 可信代理来源；内部正常请求携带 `X-Forwarded-Proto: https`，启动器以同样方式轮询就绪，再启动测试。原始 HTTP 负例使用独立上下文、关闭自动跟随重定向。该方案验证的是应用的可信代理契约，不等同于真实 TLS 握手测试。
   发布脚本的内部探针仅在确认目标已有可信 loopback 配置、监听地址及 IPv4/IPv6 对应关系，且前置代理覆盖客户端传入的 `X-Forwarded-Proto` 后采用同样方式；不得自动修改生产信任配置。公网探针继续使用 HTTPS。不要把 `/healthz` 提前放到全局安全策略之前，也不要对全部 loopback 页面豁免 HTTPS。
2. **临时端口测试仅改变监听端口。** CMS 空结果的契约测试保留主 E2E 构建使用的公开 origin，只调整 `PORT` 和本地请求地址。构建 manifest 与运行时 origin 仍严格匹配；不增加测试专用的校验跳过开关。
3. **测试子进程显式使用 CI 环境。** 普通 E2E 和 formal 的构建、启动环境都显式设置 `DEPLOY_ENVIRONMENT=ci`。普通 E2E 使用固定 loopback origin；formal 保留正式 HTTPS origin 的元数据契约。父进程及最终发布构建继续使用真实 staging/production 环境和准确公开 origin。

候选文件：`scripts/deploy.sh`、`playwright.config.ts`、`playwright.formal.config.ts`、新增的本地测试启动器、`tests/e2e/contracts.spec.ts`、`tests/formal/production-origin.spec.ts` 及对应测试。优先修正消费者；`server/request-policy.mjs`、`config/public-site.mjs` 的安全校验作为保护边界，确需改变须重新审阅范围。

### 验收标准

- 父环境分别为 staging、production 时，普通 E2E 的构建和服务能够启动；测试子进程为 ci，最终发布构建仍保留父环境的严格校验。
- 模拟依赖正常时，内部健康探针取得预期 JSON，版本探针读到本地目标版本；依赖异常或版本不符时，仍明确失败并进入原有回退判断。用本地隔离夹具验证脚本，不实际部署。
- formal 的就绪、页面和请求均命中本地进程；浏览器与服务端外连保护阻止误访问真实站点或接口，重定向断言不跟随到公网。
- 公网语义下 HTTP GET/HEAD 仍为固定 HTTPS 308，明文非安全方法仍被拒绝；不可信来源伪造转发头不能绕过。正式环境缺失或错配 manifest 仍在监听前失败。
- 临时端口 CMS 空结果测试真正监听成功，并返回预期 404；不以静态回退伪造空内容。
- 先通过定向回归及两种父环境矩阵，再在隔离测试依赖下完整执行一次 `npm run verify:release` 并取得 exit 0；保留完整日志及最终构建 origin 核验。后续有部署动作时，仍对当次最终候选执行发布门禁。

交付：三个 P1 的复现与修复对照、探针和代理信任负例、完整门禁结果、最终构建身份。尚待实际发布前核对的可信代理条件须单独列出，不能标为已上线解决。

## 第二阶段 图片视频与加载

### 先建立可比较的性能基线

`public/about/gallery` 有 157 张原图，文件合计约 16.10 MiB；这不是首页或 About 首屏实际下载量。图库已使用懒加载，但展示和放大预览共用原图。首页 `index.webp` 约 0.20 MiB；产品视频已有分段按需加载，不能仅根据资源目录大小认定首屏不达标。

先修正性能工具的运行前提：`config/lighthouse.cjs` 目前只启动已有构建，没有固定公开 origin 和部署环境；`scripts/lighthouse-runner.mjs` 不负责构建。应使用独立、明确的 CI 构建及匹配运行环境，桌面和手机串行使用同一测试 origin/端口，或各自使用隔离构建目录；禁止复用来源不明的 `dist`。这一项是阶段 2 的前置工作，Lighthouse 本身不在现有 `verify:release` 中。

沿用现有八个审计路由，补充英文 About 的图库交互检查。在相同机器、浏览器、节流和缓存规则下，每个路由桌面/手机各跑 3 次并记录中位数，保存 LCP、CLS、TBT、请求数和传输字节；另外分别记录“未滚到图库、图库进入视口、打开一张大图”三个状态。开发服务器启动耗时不计入页面性能。

长期体验目标参考真实访问第 75 百分位：LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1。Lighthouse 的 TBT 仅作实验室交互性能参考，不能替代真实 INP，也不能据此宣布线上 Core Web Vitals 达标。[Google Web Vitals 说明](https://web.dev/articles/vitals)

### 按收益实施

1. **图库优先。** 保留全部 157 张原图、顺序、布局、双语 alt 和宽高比例；生成独立的展示尺寸资源，按实际展示尺寸与像素密度选择，不覆盖原图。链接继续指向原图，桌面悬浮、键盘和手机弹窗在查看时取原图。必须同步修改 `gallery-preview.ts`，不能继续把缩略图的 `currentSrc` 当作放大源。
2. **再处理实际首屏瓶颈。** 按瀑布图决定是否增加首页响应式图片、调整首段视频预加载或字体加载顺序。保留视频 poster、分段加载、离屏暂停与现有设计；字体遵守现有同源 CSP，不新增内联事件或扩大资源白名单。基线没有显示收益的项目不改。
3. **将测量结果转为预算。** 在性能改动前，记录每个重点页面的基线值、正常波动和验收上限，写入现有 Lighthouse 校准机制；候选值在改动前冻结，不在失败后放宽阈值。当前 observe 模式的警告阈值不等于性能已经通过。

候选文件：`src/components/about/AboutScrollGallery.astro`、`src/data/about/gallery-images.ts`、图库派生资源及其生成脚本、`src/scripts/about/gallery-preview.ts`；按测量结果再决定 `HomeHero.astro`、`ProductVideoSequence.astro`、`product-video-media.ts`、字体相关组件/脚本。性能配置和 runner 单独列入文件合同，不扩张为全站重构。

### 验收标准

- 157 张原图逐文件 hash、数量、顺序及显示比例保持；派生资源无缺图，重复生成结果可复现。
- 展示状态使用合适尺寸资源，图库展示资源的总传输量小于同场景基线；打开单张图才触发该图的原图加载，不批量预取所有原图。浏览器懒加载提前量以实测记录，不要求所有视口外图片零请求。

2. **主要字段集中显示。** 中文首层保留姓名、电话、咨询服务、需求描述、隐私同意；英文首层保留姓名、邮箱、咨询服务、需求描述、隐私同意。公司/品牌及备用联系方式归入“补充信息（选填）”，保持原有 API 字段和必填校验。可选字段有错误时自动展开并定位，已填内容不丢失；无 JS 时仍可展开访问全部字段。
