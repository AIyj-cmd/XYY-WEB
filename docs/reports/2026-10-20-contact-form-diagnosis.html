原描述判断实际代码与证据
第一次返回 503 / storage_unavailable基本证实生产日志确认对应时段的 503；本地及部署代码存在相同错误码与文案。访问日志未记录响应体。
说明数据库临时写不进去证据不足配置无效、下游非 2xx、网络异常、5 秒超时、JSON 解析或响应契约异常，都可能返回相同 503。
503 一定没落库，重试不会重复推断不成立下游可能已保存，但响应超时或丢失。网站接受下游 duplicate=true；本机接收端有电话去重，但该文件有未提交修改，未核对生产接收端。
Proxy-agent 证明是 nginx 故障无法据此定位相同 JSON 由应用主动生成，代理头不能确定故障组件。现场有同秒应用异常记录。
表单由 JS 动态生成，必须逆向三层脚本不准确HTML 已包含表单与 action；JS 接管校验和 JSON 提交。源码模块拆分存在，但未核实浏览器端所述三层 chunk 链路及具体文件名。
接口是 POST JSON，中文姓名、电话、需求、隐私必填正确中文邮箱选填；手机号/座机校验规则存在。website 为隐藏蜜罐字段，正常填写应为空。
隐私值可传 on 或 true；校验会返回字段需要修正仅支持字符串 "on" 或 "true"，不接受布尔值 true。服务端校验失败返回 error + code，没有 field。
success===true 是唯一成功标准不完整客户端同时要求 response.ok。蜜罐非空会返回成功但丢弃请求；下游重复线索也可能返回成功。
等待 5 秒重试；无验证码、CSRF token部分属实网站没有自动重试，客户端超时为 15 秒。未见验证码或专用 CSRF token，但有蜜罐、限流、JSON 格式限制、8 KiB 上限和服务端校验，不能等同“没有防护”。

05建议处理顺序

  1. 核对线索接收端的实际部署与数据目的地优先核对

    确认官网应调用哪套接收服务，核定地址、认证、数据与迁移状态。配置切换应建立在接收端已可用的证据上；本次尚未实施。

  2. 保留脱敏，同时改善故障可定位性优先改进

    为超时、网络异常、下游拒绝和响应解析失败记录不同类别，增加耗时与请求关联编号；把不能确认保存结果的异常记录为“结果未知”，避免误写成“确定未保存”。

  3. 在可靠去重基础上评估超时与重试稳定性改进

    核实生产去重或幂等保障，验证“已写入但响应丢失”等情形，再调整下游 5 秒与客户端 15 秒之间的预算。不能用盲目自动重试代替故障定位。

  4. 补充提交脚本失效时的表单兜底次要体验改进

    当前原生表单编码会被 JSON-only 接口以 415 拒绝，缺少有效的无 JS 成功提交路径。可另行完善，但没有证据表明它导致了此次 503。
