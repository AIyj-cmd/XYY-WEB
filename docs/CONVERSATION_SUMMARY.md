# 新亦源官网项目对话总结

更新时间：2026-08-14

## 文档用途

- 本文按主题汇总本次长对话中已经讨论、确认、执行和暂缓的事项，方便后续快速恢复上下文。
- 当前代码、环境、验证结果和下一步任务以项目根目录 `DEV_STATE.md` 为唯一实时依据；本文主要保存决策背景和演进过程。
- 本文不记录密码、Token、API Key、私钥、Cookie、真实 `.env` 内容或其他敏感信息。
- 历史数据、设计稿和部署方案如果后来已被替换，会在对应条目中说明，不能直接作为当前上线口径。

## 一、项目目标与定位

- 项目是新亦源供应链官网，核心服务对象为鞋服品牌及相关零售、电商和门店业务。
- 官网不只是展示企业信息，还承担服务选择、案例证明、咨询转化、SEO/AEO/GEO内容承载和后台内容维护。
- 首页负责建立信任并解释新亦源的整体能力；产品页负责帮助客户根据业务问题选择具体服务；专题页负责解释单项仓配方案。
- Directus 是当前官网内容后台，前端应优先显示后台已发布内容，静态数据仅作为 CMS 不可用时的故障回退。
- 当前测试环境仍使用 PostgreSQL 16；Oracle 19c 迁移方案和脚本已准备，但数据库迁移尚未在当前环境执行。

## 二、技能库与营销能力整理

- 对原始 `agency-agents-zh` 角色库进行了营销、销售和官网推广方向的筛选。
- 重点查看和讨论过以下能力：
  - `marketing-growth-hacker`：获客、激活、留存、变现、增长实验和优先级管理；
  - 跨平台社交媒体运营；
  - 官网营销、SEO、内容推广和品牌传播；
  - `marketing-aeo-foundations`：`llms.txt`、AI爬虫可访问性和AI搜索基础设施。
- 讨论过如何调用这些技能，以及它们分别适用于增长实验、社媒内容、官网推广、SEO/AEO和销售转化的场景。
- 对技能库分析内容曾整理过 Markdown 报告；当前官网代码库中的长期事实仍应以项目文档和 `DEV_STATE.md` 为准。

## 三、首页设计与内容演进

### 1. 首页首屏

- 首屏定位由普通物流介绍调整为鞋服供应链专业能力表达。
- 品牌标签、标题和说明逐步统一为鞋服仓配语境：
  - 品牌名称与主标题在 HTML 语义上分开；
  - 主标题不把品牌名、服务名和关键词连续堆叠；
  - 标题保持粗体和白色，不显示不需要的逗号。
- 首屏服务说明覆盖入库质检、库存管理、订单履约、退货处理、二次上架、多平台和多仓协同。
- 首屏行动按钮统一为“获取仓配方案”，导航栏右侧重复按钮已取消。
- 顶部导航由通栏导航优化为居中悬浮胶囊导航，保留原有导航内容，只改变视觉形式。
- 首屏强调真实仓储场景，不以大面积深蓝遮罩掩盖仓库照片。

### 2. 统一业务数据口径

- 当前品牌合作口径统一为 `150+`。
- 当前直营仓储规模口径统一为 `54万㎡`。
- 当前员工规模口径统一为 `1500+`。
- 仍在官网使用的重要口径包括：
  - `45万+` 管理 SKU；
  - `10000+` 覆盖门店；
  - `6000+` 覆盖城市；
  - `15年` 鞋服供应链经验；
  - `99.99%` 发货准确率；
  - `99.99%` 库存准确率；
  - 单仓单日峰值 `50万单/日`。
- 历史页面中出现过 `140+`、`50万㎡+` 等旧口径，后续已要求统一替换，不能重新恢复旧值。

### 3. 能力数据与履约流程

- 首页能力区由单纯数字展示升级为仓储管理、商品管理、质检履约、服务网络和库存协同的业务说明。
- `45万+管理SKU` 被确认为鞋服行业的重要能力，应比单纯仓库面积更突出。
- 左侧“15年”卡片从装饰性年份展示改为鞋服供应链经验与仓储管理、订单履约、退货处理、库存协同能力说明。
- 正向履约流程最终统一为：
  - 订单接入；
  - 智能分仓；
  - 波次拣货；
  - 出库复核；
  - 包装出库；
  - 物流路由；
  - 签收回传。
- 退货质检与修复不再混入正向“订单到签收”流程。
- 流程动画采用蓝色基础线，滚动进入区域后由橙色线从左向右覆盖，节点依次点亮。

### 4. 首页核心解决方案

- 首页方案体系统一为四项：
  1. 鞋服云仓；
  2. 退货质检与瑕疵修复；
  3. 物流数字化能力；
  4. 运到智能寄件平台。
- 四个模块逐步统一了“客户问题、服务名称、核心价值、能力说明、适用场景、行动入口”的内容骨架。
- 鞋服云仓重点表达多平台订单、多SKU管理、大促峰值、门店补货、库存同步和智能仓储。
- 退货质检重点表达标准质检、分级处置、九大修复专区、复检和二次上架。
- 退货相关时效最终要求按照资料库和已确认业务口径展示，不能擅自恢复未经确认的常规/加急拆分。
- 物流数字化模块改用真实系统截图，不再以仓库建筑照片或AI概念图代表系统能力。
- 运到智能寄件平台改用真实物流系统、订单对接、预警和报表截图，不再使用低清旧版长信息图。

### 5. 客户案例、FAQ和转化

- 首页合作案例从四个扩展为六个已确认品牌。
- 首页卡片封面与案例详情封面要求保持一致，以首页已确认封面为准。
- 已明确删除不应继续出现的旧品牌内容，后台已发布案例应优先于静态回退。
- FAQ 改为左右结构和手风琴交互，首页只保留最重要的6至8个问题，不再全部展开成长文章。
- FAQ 问题顺序按照“是否适合、解决什么、是否有证据、如何合作”的客户决策路径组织。
- FAQ 后原有独立深蓝转化区曾被删除，咨询热线移到FAQ左侧行动区域，页面最终只保留必要页脚内容。
- 后续又在产品页保留最终咨询CTA，因此首页和产品页的转化区不能机械复制。

## 四、产品页设计演进

### 1. 产品页定位

- 产品页从“产品资料汇总页”改为“产品决策中心”。
- 产品页核心任务是帮助客户判断需要哪项服务、理解服务组成、了解可组合关系并进入专题页或咨询。
- 产品体系统一为四项核心解决方案，不再把“物流云数字能力”和“物流云数字供应链”作为两个平级产品。

### 2. 产品页首屏

- 首屏使用真实仓库照片，不使用纯深蓝SaaS式背景。
- 首屏标题围绕“一套鞋服供应链能力，覆盖商品从入仓到再次销售”。
- 删除了右侧重复白色服务卡、底部胶囊导航和过重的生命周期底栏。
- 实力数据改为按钮下方轻量一行展示，不再使用大面积深色数据卡。
- 右侧仓库场景热点用于解释挂装仓储、库存协同、订单履约和退货回流；热点应支持键盘访问和移动端点击，不依赖悬停。
- Hero主体结构最终要求冻结，不再频繁更换背景、标题和左右布局。

### 3. 服务选择区

- 服务选择区曾从四张等权卡片调整为“客户问题列表、推荐方案、真实图片”的三栏选择器。
- 生命周期区域最终从服务选择区上方完整删除，避免成为第二条导航。
- 标题右侧重复说明已删除，问题列表、中间方案和右侧图片进入同一个容器。
- 左侧问题按四类客户问题组织：
  - SKU多、平台多、大促波动；
  - 退货率高、异常类型复杂；
  - 平台、仓库和物流数据分散；
  - 门店寄件、退仓和承运商管理困难。
- 推荐方案区域使用“对应问题XX·推荐方案”和“为什么推荐”，保留原有业务数据和切换逻辑。

### 4. 鞋服云仓模块

- 顶部信息最终统一为纵向左对齐：编号、服务名称、英文标签、主标题、说明文字。
- 取消右侧超大浅色编号和模块顶部生命周期进度条。
- 仓库实景大图和能力列经过多轮调整，最终方向为左侧纵向能力列配右侧放大的真实大图。
- 三项能力为商品管理、订单履约、系统与风控；不使用卡片背景和阴影。
- 四项关键数据继续叠加在图片底部。
- “查看鞋服云仓完整方案”和相关案例入口保持同一行动区域。

### 5. 退货质检模块

- 删除模块顶部商品生命周期行。
- 标题区样式与鞋服云仓统一，避免标题被压成窄列逐字换行。
- 质检数据包括 `135+种异常识别`、`7大类异常分类`、`9个修复专区` 和 `90%瑕疵修复成功率`。
- 处理流程包括拆包登记、标准质检、分级、清洁修复、品牌标准复检和二次上架/退供/报废。
- 数据和流程逐步叠加到真实质检作业图片中，减少左侧零散信息块。

### 6. 产品页整体视觉规则

- 中间内容以白色和浅灰蓝为主，深蓝仅用于Hero局部、最终CTA和页脚。
- 避免每一屏都使用同样圆角卡片、边框和标题模板。
- 图片、数据、流程、系统截图、编号列表和目录导航应根据内容选择不同表现形式。
- 区块内部线条和背景切换曾造成明显分割感，因此要求减少无意义边框、保持背景连续并降低02至04章节标题权重。
- 产品页及仓配下拉专题页共享统一滚动显示动画，移动端和减少动态效果模式必须直接可读。

## 五、关于我们、案例、新闻和期刊

- 关于页仓网在部分区域曾因动画触发过晚而不可见，后续统一了服务页滚动显示逻辑。

- 案例详情拥有独立可抓取URL，便于搜索引擎收录、分享和转化统计。
- 新闻栏目继续支持后台发布文章，不显示“历史新闻已下线”一类阻止发布的静态提示。
- 森林期刊后台从静态封面路径和PDF路径逐步升级为可上传封面与附件的文件字段。

## 六、Directus后台与内容维护

### 1. 后台中文化

- Directus左侧集合名称已要求统一为中文。
- 集合内部字段名称、提示和选项也要求中文化，减少维护人员理解成本。
- URL标识用于生成文章、案例等内容的可访问路径，应使用稳定、简短、唯一的英文或拼音slug。

### 2. 内容模型

- 后台从最初少量集合扩展为19个业务集合。
- 已讨论并纳入后台维护的内容包括：
  - 首页统计和内容；
  - 服务及服务专题；
  - FAQ页面与问题；
  - 合作案例、案例详情和案例数据；
  - 新闻文章；
  - 森林期刊；
  - 关于我们、发展历程和企业荣誉；
  - 仓储信息；
  - 全站设置；
  - 联系留言。
- 案例指标曾采用“一条指标一条记录”的方式，维护成本较高；后续要求以品牌为单位聚合案例详情和指标，避免重复字段。
- FAQ、案例、服务和其他后台已发布内容应在前端请求时实时显示，静态回退不得覆盖成功读取的后台数据。

### 3. 权限模型

- 网站运行时使用两枚独立的最小权限Token：
  - 内容Token只读取18个已发布内容集合；
  - 联系Token只创建联系留言，不读取历史留言。
- 管理级Token仅用于CMS初始化和权限同步，完成后应撤销，不进入长期运行环境和Git。
- 2026-08-14新增共享集合契约，统一18个公开集合、1个私有集合和19个全量集合的名称来源。
- `/healthz` 由逐一读取18个集合改为读取两枚Token的权限映射，单次Directus请求由约20次降为3次。
- 完整逐集合读取、敏感端点和越权验证仍由部署验收命令执行。

## 七、数据库与部署方案

### 1. 当前数据库状态

- 当前验收环境仍使用 PostgreSQL 16。
- 曾将“Oracle 16”口误纠正为 Oracle 19c。
- 已明确的目标架构是Web前端、服务后端和Oracle 19c数据库按部署条件分开准备。
- Oracle 19c数据库应使用已有Oracle环境，由初始化脚本创建用户、表空间和Directus所需数据结构，再由内容迁移脚本迁移数据。
- Oracle迁移脚本已经准备，但尚未在当前环境完成真实迁移、恢复和回滚验证。

### 2. 脚本包

- 曾按要求整理独立脚本包，区分数据库初始化、Web前端部署和服务后端部署。
- 部署资料需要让接收方仅凭Git仓库和脚本即可理解执行顺序，不依赖本次聊天记录。
- 数据库备份、Directus附件备份、Token轮换、模型初始化和运行权限验证必须在切换前完成。

### 3. Web运行和发布

- PM2配置文件为 `ecosystem.config.cjs`。
- Web监听地址已改为 `0.0.0.0`，端口为 `50031`。
- 当前发布脚本采用隔离Release目录、软链切换、健康检查和失败回滚。
- 未变化的大型静态资源会从上一Release复用，避免每次重新上传全部期刊文件。
- 2026-08-14新增的 `config/` 共享契约目录已加入原子发布清单，并由部署契约测试保护。

### 4. 环境文件原则

- `.env.example` 用于说明变量名称和格式，不能放真实密码和Token。
- 真实 `.env` 只存在于本地或服务器，必须被Git忽略。
- 对话中曾讨论把 `.env.example` 改名为 `.env`，但长期正确做法仍是保留安全模板、在服务器单独配置真实 `.env`，不能把真实凭据提交Git。

## 十一、关键协作约定

- 每完成一个开发任务、配置调整、测试、提交或部署动作，都要更新根目录 `DEV_STATE.md`。
- `DEV_STATE.md` 采用分点结构，记录当前做到哪里、为什么这样做、验证结果、已知问题和下一步。
- 状态记录使用中性、任务导向的表达，不使用不必要的身份称呼。
- 不把所有内容重新写进一个文件或一个模块，避免制造新的技术债。
- 不修改用户未授权的接口、路由、业务口径或其他页面区块。
- Git提交只包含项目需要的代码、配置和技术文档；提示词、临时截图、分析产物和敏感文件不得上传。
- 发布、Git推送和数据库初始化属于不同动作；除非明确要求，不因完成本地修改而自动执行外部发布。
