# CMS 全功能测试方案（2026-08-20）

## 1. 当前覆盖结论

上一轮不是所有后台菜单都做了写入测试：

- 已覆盖全部19个契约集合的 Schema、Seed、读取、权限和基础前台消费检查；
- 已完成 `news`、`directus_files` 和一条关联既有页面的 `faqs` 的创建、保存重开、发布、取消发布与删除；
- `contact_leads` 已覆盖前台创建与运行令牌边界，但没有完整覆盖后台查看、状态处理和删除；
- 其余品牌资料、首页内容、FAQ 页面、服务、仓库、案例、期刊、服务专题、关于内容、发展历程、企业荣誉和全站设置尚未逐集合执行完整写入闭环。

本方案的目标是让每个运行集合都具备可重复、可清理、能证明前后台联动的测试证据。

## 2. 环境与安全边界

### 阶段 A：隔离本地环境

- 使用一次性 PostgreSQL 数据库、Directus 12.1.1 和本地 Astro SSR；
- 运行当前仓库 Setup，导入标准 Seed；
- 所有记录使用 `【CMS全功能测试】`、`cms-e2e-<run-id>` 前缀；
- 测试结束删除测试记录、附件、联系留言和一次性数据库；
- 这是自动化开发和完整破坏性边界测试的主环境。

### 阶段 B：验收站

- 必须先备份数据库和上传目录，并获得 CMS 写入、权限同步和测试发布授权；
- 普通集合可以创建一次性记录；Singleton 只能“导出原值—修改一个安全字段—验证—原样恢复”；
- 每个创建操作立即记录集合、ID、文件 UUID 和恢复动作；
- 测试结束要求数据计数、Singleton 内容和文件库回到基线。

### 阶段 C：主站

- 默认只执行版本、健康、读取、权限和前台 Smoke；
- 不创建、删除或修改真实内容；
- 若必须做写入验收，需再次单独授权，并限定为可逆测试记录和维护窗口。

## 3. 统一前置与清理规则

每次运行前：

1. 记录应用 SHA、CMS Schema、Directus 版本、19个集合计数和文件数；
2. 运行 `cms:verify` 与 `cms:verify-runtime-permissions`；
3. 导出三个 Singleton：`homepage_content`、`about_content`、`site_settings`；
4. 准备一次性 PNG、WebP 和 PDF，记录文件哈希；
5. 开启浏览器 Console、失败请求和 Directus 日志采集；
6. 建立测试资源清单，所有创建返回的 ID/UUID 必须进入清单。

每次运行后：

1. 先取消发布，再删除测试内容及其关系；
2. 删除所有一次性文件和联系留言；
3. 精确恢复 Singleton 原值；
4. 校验测试前缀记录、测试文件和测试留言均为0；
5. 比较集合计数与基线，重新运行两项 CMS 验证和 `verify:release`。

## 4. 后台导航稳定性测试

对截图中每个菜单执行：

- 列表页连续打开和刷新5次；
- 支持创建的集合连续打开 `+` 页面5次；
- 从列表进入编辑页、返回列表、再次进入；
- 检查页面标题、表单字段、保存按钮和关系选择器均已加载；
- 记录所有 HTTP 4xx/5xx、未处理 Console Error、空白页和加载超时；
- 同时测试一次直接 URL 和一次从左侧导航点击进入。

验收标准：非预期失败请求为0，页面打不开或表单空白为0，保存后重开数据一致。

## 6. 每个普通集合的统一 CRUD 断言

所有非 Singleton 集合至少执行：

1. 空表单保存：必填字段必须明确报错；
2. 创建 Draft：API 和列表存在，公开前台不存在；
3. 编辑全部可编辑字段：保存后返回列表并重开，值完全一致；
4. 唯一字段：重复 `slug`、`content_key` 或 `issue` 必须被拒绝；
5. 发布：下一次 SSR 请求显示，结构化数据和发现文件按集合契约更新；
6. 排序：相邻两条记录交换排序后前台顺序同步；
7. 取消发布：列表/详情/资源引用按契约消失；
8. 删除：记录、关系和测试文件无孤儿残留；
9. 桌面1440×900和移动430×932各验证一次前台消费者。

## 7. 关系、富文本与安全测试

- FAQ 与 FAQ 页面关系必须保存、重开并能更换；
- 六类文件字段必须保存 UUID 关系：案例、新闻、期刊封面、期刊 PDF、服务 Hero、历程/荣誉图片；
- 删除仍被引用的文件时必须记录 Directus 行为，并确认前台不会产生无提示断图；
- 富文本分别输入标题、列表、链接和允许的基础格式，前台渲染正确；
- 输入 `<script>`、事件属性和危险 URL，前台不得执行；
- Claim 占位符在允许字段中必须替换，未知或未解析的 `{{...}}` 视为失败；
- 内容令牌不得创建/修改/删除，联系令牌不得读取内容、文件或历史留言。

## 8. 自动化实施结构

建议新增一个独立命令 `npm run test:cms:functional`，分为四层：

1. `cms-functional-preflight`：启动隔离 CMS、Setup、Schema/权限验证和基线快照；
2. API 契约测试：逐集合验证必填、唯一、关系、状态过滤和权限；
3. Playwright 后台测试：真实操作导航、`+` 页面、文件选择器、保存重开和删除确认框；
4. Playwright 前台测试：桌面/移动消费者、资源代理、发现文件和 Console/Network；
5. `cms-functional-cleanup`：按清单删除并对基线做深度比较，即使中途失败也必须运行。

测试用例不得依赖固定数据库 ID；只能使用本次运行返回的 ID、UUID 和唯一前缀。

## 9. 最终通过标准

- 13个 active 集合、`contact_leads` 和 `directus_files` 均有对应写入或 Singleton 可逆测试；
- 所有后台列表页和适用的 `+` 页面稳定打开；
- 所有保存内容在重开后一致；
- Draft/Published/未来发布时间过滤符合契约；
- 六类文件关系、图片和 PDF 交付全部正常；
- 前台桌面、移动、sitemap、llms.txt 和结构化数据无测试泄漏；
- 非预期 Console Error、HTTP 4xx/5xx、断图和未解析 Claim 均为0；
- 清理后测试记录、附件和留言为0，Singleton 与集合计数恢复基线；
- `cms:verify`、运行权限审计和 `verify:release` 全部通过。

## 10. 建议执行顺序

1. 先实现隔离环境自动化骨架和强制清理；
2. 按“无文件集合 → 关系集合 → 文件集合 → Singleton → 联系留言”顺序补测试；
3. 隔离环境连续通过两次后，再申请验收站写入权限；
4. 验收站完成一次完整闭环并清理后，主站仅做只读 Smoke；
5. 主站任何写入、迁移、权限同步或部署继续单独审批。
